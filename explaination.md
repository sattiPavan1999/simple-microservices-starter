The diagram shows the three tiers. Below is what each piece is and why it exists, following one request from your browser to the database.

1. Network (vpc.tf)
VPC (10.0.0.0/16) is your own isolated network inside AWS. Everything else lives in it.
Six subnets, in 2 availability zones. There are three tiers (public, private, DB) with two subnets each. Two zones are required because RDS and EKS both need subnets in at least 2 zones.
Internet gateway is the door between the VPC and the internet. Only the public subnets use it.
NAT gateway (in a public subnet, with an Elastic IP) lets private resources start connections to the internet, but nothing from the internet can start a connection to them. Your nodes need it to join the EKS cluster and to pull images from Docker Hub.
Route tables are what make a subnet public or private. The public route table sends 0.0.0.0/0 to the internet gateway. The private one sends it to the NAT gateway. The DB route table has no internet route at all, so the databases can’t reach the internet or be reached from it.
2. Databases (rds.tf)
Two RDS PostgreSQL instances, one per backend, copying your docker-compose layout (users-db, products-db). RDS creates users_db and products_db itself, so Prisma can migrate straight away.
DB subnet group tells RDS to use only the DB subnets.
Parameter group turns off rds.force_ssl. PostgreSQL 16 on RDS requires SSL by default, and your apps connect without it.
Random passwords are generated by Terraform. The full DATABASE_URL for each service is saved in SSM Parameter Store as an encrypted string. That’s where you copied it from into the Kubernetes Secrets.
Not public, and encrypted. publicly_accessible = false means no public address.
3. EKS (eks.tf)
Control plane is the Kubernetes API, run and patched by AWS. It reaches your VPC through network interfaces in the private subnets. Its public endpoint is why kubectl works from outside the VPC.
Two IAM roles. The cluster role lets EKS manage AWS resources for you, such as creating load balancers. The node role lets EC2 instances join the cluster, set up pod networking, and pull from ECR. It also allows SSM shell access without SSH.
Managed node group is the 2 × t3.medium EC2 instances that run your pods. They sit in the private subnets only, so they have no public IPs.
Add-ons. vpc-cni gives each pod a real VPC IP, coredns handles service name lookups, kube-proxy handles service networking, and the pod identity agent is installed but unused so far.
Subnet tags (kubernetes.io/role/elb) tell Kubernetes which subnets to place load balancers in.
4. Security groups (security_groups.tf)

Security groups are firewalls that allow traffic from specific sources.

The rule that does the real work today is rds_from_eks: the EKS cluster’s security group is allowed to reach port 5432 on both databases. Nothing else can reach the databases, and they have no public path anyway.

The load balancer, frontend and per-service backend security groups from security_groups.tf are not actually used by your current setup. Kubernetes creates its own security groups for the load balancers, and the pods use the cluster’s security group. I created them because they’re the standard layout for a setup with an ALB and EC2 or ECS, and they’d be used if you switched to that. For a clean practice setup, you can delete them.

One limitation: any pod can currently reach both databases, not just its own. Enforcing “users pods only reach users_db” would need Security Groups for Pods, which is beyond this practice setup.

5. Kubernetes layer (the YAML files)
Namespace microservices groups everything.
Secrets hold the DATABASE_URLs, so no passwords sit in YAML.
Deployments run 2 pods each. The backends have an init container that runs the migration and seed before the app starts.
Services of type LoadBalancer make Kubernetes call AWS and create a load balancer in the public subnets for each service. The load balancer forwards port 80 to a port on the nodes, which forwards to the pod (80:32702/TCP in your kubectl get svc output).
ConfigMap gives the frontend the two backend URLs.
The full request path
Your browser requests the frontend load balancer in the public subnets.
It forwards to a frontend pod on a private node, which returns the HTML and /config.js with the backend URLs.
Your browser’s JavaScript then calls the users and products load balancers directly.
Those forward to the backend pods, which connect to their RDS instance over the private network.
RDS checks its security group, which allows the EKS cluster, and returns the rows.
When a node needs a Docker Hub image, it goes out through the NAT gateway.
